## Что уже есть в Vuls, а что ещё нужно доказать

Есть Telegram reporter, отчёты diff и настройки БД, включая KEV. Наличие diff не доказывает durable-доставку или защиту от ложного закрытия находки после неудачного скана. См. [report](https://vuls.io/docs/en/usage-report.html).

Настройка сложнее целевого мастера первого запуска. Документация vulsctl предлагает Docker-обёртки; это один из способов установки, а не обязательное требование всех режимов Vuls. Стоимость минимальной конфигурации для нашего VPS ещё не измерена. См. [vulsctl](https://vuls.io/docs/en/install-with-vulsctl.html).

WordPress-путь использует WP-CLI и API WPScan, а исходное ТЗ требует Wordfence. Это подтверждается [документацией](https://vuls.io/docs/en/usage-scan-wordpress.html) и [кодом на проверенном commit](https://github.com/future-architect/vuls/blob/031f637cadf5f0c26b3387578172d9c8aa4afcd6/detector/wordpress.go). Условия использования WPScan API нужно проверять отдельно; бесплатность для всех наших пользователей не установлена.

### Найденное ограничение Telegram reporter

В [reporter/telegram.go, строки 74–79](https://github.com/future-architect/vuls/blob/031f637cadf5f0c26b3387578172d9c8aa4afcd6/reporter/telegram.go#L74-L79) проверка HTTP-статуса объединена с транспортной ошибкой через `&&`. Если HTTP-запрос завершился без транспортной ошибки, ответ 400/429/500 не приводит к возврату ошибки из этой ветки. При транспортной ошибке с `resp == nil` вызов проверки ответа разыменует nil. JSON-поле `ok` ответа также не проверяется в этом методе.

Это статический вывод по функции, без воспроизведения и без полного аудита проекта. Встроенную доставку нельзя считать соответствующей требованиям надёжности до исправления и тестов. Варианты: upstream-исправление либо собственный notifier поверх JSON-отчёта. Из этого не следует необходимость переписывать весь Vuls.

## Особенности Trivy, влияющие на выбор

Trivy учитывает источник OS-пакета и использует vendor advisories для уменьшения ложных срабатываний на backports. Сторонние репозитории требуют отдельного внимания: документация описывает пропуски и ограничения эвристик. Поэтому «Trivy поддерживает Ubuntu» не означает покрытия любого ПО на Ubuntu. См. [официальную документацию](https://trivy.dev/docs/latest/guide/scanner/vulnerability/).

Для OS-only rootfs-сканирования предусмотрен режим без полного обхода дерева файлов; приложения следует сканировать отдельно по выбранным каталогам. См. [rootfs](https://trivy.dev/docs/latest/guide/target/rootfs/).

При выборе поставки нужно учесть подтверждённый авторами supply-chain инцидент марта 2026 года: затрагивались определённые бинарники/образы и Actions. Это исторический инцидент, а не утверждение о компрометации текущей версии. Нужны проверенная версия, проверка артефакта и отказ от плавающего `latest`; текущую допустимую версию определять перед реализацией по [официальным advisories](https://github.com/aquasecurity/trivy/security/advisories) и [описанию инцидента](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23).

GitHub API на дату проверки: создан 2026-11-02; HEAD указан выше. Возраст не доказывает низкого качества, но эксплуатационная зрелость не установлена. В документации есть модель организаций, SSH-доступ, опциональный внешний скан и подготовка задач исправления; это шире нашего локального сервиса. См. Перед заимствованием необходимо проверить фактические побочные эффекты всех адаптеров и отделить аудит от любых путей применения исправлений. Наличие в проекте инструкций или генерации fix-плана само по себе не означает автоматического исполнения. Поддержка нужных релизов Debian/Ubuntu, Telegram, scheduler и поведение при отказах пока не приняты.

## Первоначальный план проверки

Проверка OS-сканирования на Ubuntu выполнена; остальные пункты ниже остаются планом, а не принятыми результатами. Итог текущего этапа находится в [runtime-отчёте](SCANNER_EVALUATION_2026-11-06.md).

Сравнить Vuls и минимальную оболочку Trivy на одинаковых изолированных Debian/Ubuntu VM. Никакой установки на рабочие серверы для этого не требуется. Проверить:

1. Холодный запуск: зависимости, загрузки, диск, RAM и время; повторный скан.
2. Backported fix и пакет стороннего репозитория; доступный фикс отдельно от установленного.
3. Новую CVE, добавление KEV, отсутствие фикса, появление фикса и повторную проверку.
4. Битый/пустой результат, timeout, stale feed: старая находка не закрывается.
5. Telegram 429/500/timeout, перезапуск между событием и доставкой, baseline без массового спама.
6. Команды сканирования не обновляют пакеты, не меняют настройки и не рестартуют службы.

Если Vuls проходит с небольшими доработками, предпочтителен интеграционный проект вокруг него. Если объём обвязки и эксплуатационные издержки сопоставимы с собственным сервисом, выбрать Trivy + небольшой слой состояния/уведомлений. Архитектуру и fork пока не утверждали.
