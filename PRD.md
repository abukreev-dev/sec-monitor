# Security Monitor — PRD

Версия: 0.1, 2026-11-06. Статус: **план согласован; реализация и runtime-приёмка MVP**.

Основания: [исходное ТЗ](TZ_Security_Monitor_VPS_Codex_2026-11-06.md), уточнения владельца, [сравнение готовых решений](docs/RESEARCH_GITHUB_2026-11-06.md) и [runtime-проверка на Ubuntu](docs/SCANNER_EVALUATION_2026-11-06.md). Согласован собственный продукт поверх Trivy, без форка на старте. Реализованы CLI, state/outbox и адаптеры; OS-контур проверяется на Ubuntu 24.04 x86_64. Debian и полная приёмка всех интеграций остаются открыты. Текущая версия pre-release; фактические ограничения — [COVERAGE](docs/COVERAGE.md).

## 1. Продукт и пользователь

Бесплатный self-hosted open-source монитор известных уязвимостей Linux-сервера. Администратор клонирует репозиторий, выполняет первичную проверку, настраивает уведомления и включает периодический мониторинг. После установки не требуется участие разработчика или AI-агента.

Основной пользователь — администратор одного или нескольких VPS с сайтами, приложениями и, при наличии, контейнерами. На каждом сервере независимый экземпляр. Для нескольких серверов допустим общий Telegram-чат с разными псевдонимами хостов.

Пользователь получает ответ: что на этом сервере затронуто; насколько уверенно; что опаснее; есть ли исправление именно для его источника пакетов; что сделать вручную; подтвердилось ли устранение после действий администратора.

## 2. Подтверждённые решения

| ID | Решение |
|---|---|
| D-01 | Публичный open-source проект, самостоятельный запуск из репозитория |
| D-02 | Только Linux; для MVP достаточно Debian и Ubuntu |
| D-03 | Продукт только обнаруживает, уведомляет и даёт инструкции |
| D-04 | Монитор не обновляет ОС, пакеты, сайты, зависимости, образы или конфигурацию сервера |
| D-05 | Готовые решения изучаются до выбора собственной реализации |
| D-06 | Текущий этап — документы и обсуждение, без установки на серверы |
| D-07 | Свой `sec-monitor` поверх готового сканера; минимальный форк только при доказанной необходимости |
| D-08 | Trivy как движок; реализация, эксперименты на выделенном Ubuntu-хосте и публичный GitHub разрешены |

Уточнение D-06: после исследования отдельно согласованы реализация и эксперименты на Ubuntu-хосте. Допустима установка самого монитора; обновления серверного ПО, изменение приложений и применение исправлений остаются запрещены.

Запрет D-04 — граница продукта, а не переключатель `auto_update=false`. Функций применения исправлений, кнопок «исправить» и выполнения команд из advisories в продукте нет. Монитор не отключает уже настроенные владельцем механизмы обновлений.

## 3. Ценность и предел обещаний

Ценность — применимые к локальному стеку уведомления с доказательствами и понятным действием, небольшая нагрузка, явные пробелы покрытия, отсутствие повторяющегося шума.

Успешный скан не означает, что сервер безопасен или не скомпрометирован. KEV означает известную эксплуатацию уязвимости в мире; это не доказательство взлома данного сервера. Нет обещания покрытия неизвестных уязвимостей, любого стороннего пакета или всех самосборных бинарников.

## 4. Основной сценарий первого запуска

Названия команд ниже — проектируемый интерфейс; сейчас они не реализованы.

| Шаг | Действие | Результат и граница |
|---|---|---|
| 1 | Клонировать репозиторий стабильного релиза | Локальный код; фоновые задачи ещё не включены |
| 2 | `./security-monitor discover` | Проверка Linux, версии, архитектуры, ресурсов, пакетной базы и доступных прав; выбранные области поиска |
| 3 | `./security-monitor scan` | Первичный локальный отчёт и coverage; Telegram не требуется |
| 4 | `./security-monitor configure` | Псевдоним сервера, timezone, Telegram, необязательный Wordfence, области сканирования и интервалы |
| 5 | `./security-monitor install --dry-run` | Точный план установки самого монитора, права, зависимости, пути и systemd units |
| 6 | `./security-monitor install` | Только явно запрошенная установка монитора; без включения периодических сканов |
| 7 | `security-monitor notifications test` | Проверка Telegram; без реквизитов доступен локальный режим |
| 8 | `security-monitor service enable` | Явное включение systemd-таймеров; baseline и последующие события |
| 9 | `security-monitor status` | Находки, покрытие, свежесть, ошибки и состояние доставки |

Холодный запуск должен объяснять отсутствие Python/сканера и размер необходимых загрузок. `discover`/`scan` не вызывают системный пакетный менеджер для установки или обновления зависимостей. При отсутствии инструментов — доступная частичная инвентаризация и инструкции подготовки; отдельный явный bootstrap, если он понадобится, согласуется как часть установочного интерфейса.

«Read-only» относится к проверяемой системе. Монитор может писать свои отчёты, БД, кэш и логи в выделенные каталоги. Загрузка vulnerability databases разрешена; обновление исполняемого кода под видом обновления базы — нет. Внешние запросы и назначение передаваемых данных описаны до подключения интеграций. Без сети/свежей базы результат помечается соответствующим ограничением.

## 5. Матрица Linux и режимы

Предлагаемая матрица первого релиза: Debian 12/13, Ubuntu LTS 22.04/24.04/26.04, systemd, x86_64. Это список кандидатов для тестирования, а не уже подтверждённая поддержка. Основание выбора актуальных веток: [Debian releases](https://www.debian.org/releases/) и [Ubuntu release cycle](https://ubuntu.com/about/release-cycle). Финальную матрицу сокращаем или принимаем по результатам проверки сканера и установщика.

ARM64 — открытый вопрос. RPM-семейство, Alpine/OpenRC, rolling releases и другие Linux — вне MVP. Неподдерживаемая система получает понятный отказ от установки таймеров и явный coverage gap; обнаружение похожего пакетного менеджера не даёт права объявлять её поддерживаемой.

Состояние security support определяется по релизу и пакету, включая ограничения LTS/ESM и подключённых репозиториев. Платная подписка не обязательна; её отсутствие не скрывает недоступность отдельных исправлений. После окончания поддержки ОС монитор предупреждает, а не исправляет ситуацию самостоятельно.

Без root доступно всё, что можно достоверно прочитать текущему пользователю. Недоступные области видны в отчёте. Дополнительные права на чтение выдаются только при явной настройке; отдельный процесс с сетевыми API и Telegram не должен постоянно работать от root.

## 6. Объём MVP

| ID | Требование | Условие готовности |
|---|---|---|
| F-01 | Инвентарь ОС, пакетов, origins, архитектуры и основных сервисов | Точные версии/сборки, источник, время наблюдения, недоступные области |
| F-02 | Проверка OS-пакетов по vendor-данным с учётом backports | Исправленная vendor-сборка не объявляется уязвимой по одной upstream-версии |
| F-03 | KEV и применимость к локальному инвентарю | KEV повышает приоритет подтверждённой находки; одно совпадение имени недостаточно |
| F-04 | Фиксы upstream и фактического репозитория | Раздельные статусы; held/pinned packages и возраст metadata не теряются |
| F-05 | Telegram, baseline, дайджест и изменения | Уведомления о существенных событиях; без токена работает локальный режим |
| F-06 | История, дедупликация и очередь доставки | Перезапуск не уничтожает ожидающие сообщения; повторный скан без изменений не создаёт новые события |
| F-07 | Health и coverage | Для каждого адаптера видны last success, freshness, ошибки, отключение и причина |
| F-08 | CLI и отчёты text/JSON | `discover`, `scan`, `configure`, `status`, `health`, `doctor`, `report`, управление таймерами |
| F-09 | Безопасная эксплуатация самого монитора | Идемпотентная установка, остановка, ручное обновление, миграции, backup, rollback, uninstall |
| F-10 | WordPress при обнаружении и настройке | Core/плагины/темы, включая неактивные; без feed-ключа явное ограничение |
| F-11 | Зависимости выбранных проектов | Точные поддерживаемые lockfiles; никакого запуска кода приложения |
| F-12 | Контейнеры при включении адаптера | Используемый digest и отдельный asset; отсутствие Docker не является ошибкой |

F-10–F-12 наследуются из исходного ТЗ. Предложение порядка работ: сначала F-01–F-09, затем эти адаптеры, до публичного заявления о полном объёме. Исключение WordPress или контейнеров из первого публичного MVP требует отдельного решения; оно пока не принято.

Не обещаем автоматические vendor-адаптеры для всех панелей, PPA и самосборного ПО. Каждый обнаруженный компонент получает `covered`, `partial`, `unsupported` или `manual_review_required` с объяснением. Совпадение только названия продукта — ранний сигнал для проверки, а не доказанная уязвимость.

WordPress: безопасный разбор файлов по умолчанию; WP-CLI — только явно настроенный запуск от владельца сайта. `--skip-plugins` не исключает выполнение MU-плагинов ([официальное описание](https://developer.wordpress.org/cli/commands/plugin/list/)); его нельзя представлять как гарантию отсутствия исполнения кода. Multisite и неоднозначные slug/версии должны показывать ограничения. Предпочтительный feed из ТЗ — Wordfence V3; он требует индивидуальный ключ и соблюдение условий ([документация](https://www.wordfence.com/help/wordfence-intelligence/v3-accessing-and-consuming-the-vulnerability-data-feed/)).

Контейнеры: постоянный доступ notifier к Docker socket недопустим; способ инвентаризации и безопасный источник образа выбираются отдельно. Монитор не запускает, не пересоздаёт и не обновляет контейнеры.

## 7. Модель находки и рекомендации

Уникальность: сервер + asset + идентичность компонента + canonical vulnerability ID. Alias CVE/GHSA/Wordfence объединяется только при подтверждённой связи; разные сайты и контейнеры сохраняются отдельно.

Независимые измерения:

| Измерение | Значения/смысл |
|---|---|
| Применимость | untriaged / potentially affected / affected / not affected |
| Исправление | unknown / no fix / upstream fix / repo fix; возможны одновременно upstream и repo |
| Устранение | open / update detected pending verification / verified / mitigated / needs reverification |
| Здоровье проверки | fresh / stale / error / unsupported / disabled |

Находка содержит установленные версии, происхождение пакета, evidence, ссылки, confidence, время публикации, первого обнаружения и последней успешной проверки. Неизвестная оценка CVSS остаётся неизвестной.

Изменение установленной версии не закрывает находку до верификации. Исчезновение из выдачи, удаление asset или сбой сканера не равны устранению. Для ядра/работающих процессов отдельно учитывать разницу установленной и используемой версии; если это проверить нельзя, не обещать runtime-устранение.

P1: подтверждённая применимость + KEV либо документированные условия высокого риска. P2: прочие подтверждённые существенные риски и важные изменения исправления. P3: остальные находки и неопределённые сигналы. SYSTEM: отказ мониторинга. Точную таблицу приоритизации и thresholds согласовать до реализации.

Рекомендация — инструкция администратору со ссылкой на источник, условиями применимости и способом последующей проверки. Команды показываются как текст и никогда не выполняются. Если пакет/репозиторий или безопасное действие не определены, сообщение прямо требует ручной проверки. LLM не является обязательной зависимостью и не принимает решения о применимости.

## 8. Уведомления и наблюдаемость

Первый успешный baseline отправляется сводкой. Если среди старых находок есть P1, сводка явно выделяет их. Неуспешные области не получают baseline «всё проверено». Новая CVE, KEV, появление исправления, изменение приоритета и подтверждённое устранение создают отдельные события.

Durable outbox хранит состояние и retry/backoff. Ошибки HTTP, Telegram `ok=false` и 429 обрабатываются явно. Гарантия exactly-once поверх внешнего API не обещается: timeout после принятия сообщения может дать редкий дубль. Аггрегация и лимиты не должны молча терять P1.

Telegram передаёт только необходимое: псевдоним хоста, продукт/версию, ID, риск, применимость, исправление, инструкцию, ссылки и время. Публичного URL отчёта нет; чувствительные пути и секреты исключаются. Проверка ответа API подтверждает принятие Telegram, а не прочтение пользователем.

Self-check не обнаружит полную остановку своего VPS. Независимый heartbeat допустим как необязательная интеграция, без автоматической регистрации внешнего аккаунта.

## 9. Нагрузка, данные и безопасность

Предложение графика: лёгкие feeds/health — 15 минут; inventory/update availability — час; OS-скан — 6 часов; зависимости/образы — сутки и при обнаруженном изменении; дайджест — сутки. Периоды уточняются после измерения на малом VPS. Тяжёлые задачи сериализуются, с jitter, timeout и лимитами ресурсов.

По runtime-проверке для Trivy необходимы явное отключение телеметрии и компактный машинный формат с сохранением evidence. Обычный JSON не принимается как безусловно подходящий для малого VPS. Связанные kernel package findings группируются в уведомлениях с сохранением всех связей в состоянии. Происхождение стороннего пакета проверяется отдельно от наличия CVE в vendor-выдаче.

Системные APT metadata читаются в текущем состоянии; автоматический `apt update` в scan/таймерах MVP не выполняется. Устаревшие индексы дают `unknown/stale` для доступности пакета; инструкции могут предложить администратору обновить индексы вручную. Не путать это с загрузкой собственных CVE feeds.

Целевой стенд измерения — 1 vCPU / 1 GiB RAM. Это цель проверки, не объявленные минимальные требования. До выпуска измерить cold/warm duration, peak RSS, CPU, диск/кэш, исходящий трафик и влияние на контрольный веб-сервис. Публиковать результаты и ограничения; превышение бюджета прекращает задачу с health-событием.

Локальное состояние без обязательных PostgreSQL/Redis; предпочтительно SQLite, если выбранная основа позволяет. Секреты вне Git, права 0600, приватные данные/отчёты вне репозитория. Сетевые обработчики работают с минимальными правами; входы из feeds и имена/пути считаются недоверенными. Нет shell-интерполяции advisories, secrets scanning по умолчанию или полного бесконтрольного обхода файловой системы.

Собственные записи и миграции атомарны; предыдущий успешный результат сохраняется при ошибке. Retention ограничивает рост. Backup/restore и ручное обновление самого монитора сохраняют очередь и историю; откат схемы учитывает совместимость кода и БД. Runtime не делает `git pull`, `pip install`, обновление сканера или self-update. Администратор устанавливает проверенные релизы отдельной командой; никакого общего обновления серверных пакетов как побочного эффекта.

## 10. Open-source поставка

До публикации обязательны: выбранная лицензия, README с коротким запуском и точной матрицей, SECURITY.md, CONTRIBUTING.md, changelog, версия/теги, примеры без секретов, CI, fixtures, политика поддерживаемых версий и инструкция удаления/восстановления. Предложение для документации — английский README и русская версия; языки уведомлений RU/EN обсуждаются отдельно.

Код проекта и внешние feeds имеют отдельные условия использования. Не коммитить реальные inventory, полные сторонние feeds, токены и хосты. Для публичных tests использовать синтетические/разрешённые fixtures. Базовая работа не зависит от нашего SaaS, общей учётной записи или общего API-ключа; телеметрия разработчикам отсутствует.

Сканер поставляется проверяемым способом с фиксированной версией и проверкой артефакта; `latest` и автоматическая загрузка непроверенных исполнителей не допускаются. Результат выбора Vuls/Trivy и лицензии фиксируется до реализации.

## 11. Приёмка

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| A-01 | Чистая VM каждой заявленной ОС | Весь путь первого запуска по README без ручного редактирования кода |
| A-02 | Отсутствуют Telegram/WP/Docker/права/сеть | Понятный локальный/частичный режим, без ложного зелёного статуса |
| A-03 | Backport, сторонний пакет, stale APT metadata | Корректное evidence либо явная неопределённость |
| A-04 | Появление CVE → KEV → fix → ручная установка → повторный скан | Отдельные статусы/события, доказанное закрытие |
| A-05 | Одинаковые результаты и одна CVE на двух сайтах | Нет дублей событий; оба asset сохранены |
| A-06 | Timeout, corrupt JSON, stale feed, пропавший asset | Старые находки не закрываются как исправленные |
| A-07 | Telegram 429/500/timeout, reboot и прерванная доставка | Retry и сохранённая очередь; API-ошибка не объявляется успехом |
| A-08 | Установка повторно, остановка, upgrade/rollback монитора, uninstall | Идемпотентность и сохранность выбранных данных; чужие службы не тронуты |
| A-09 | Контроль вызываемых команд и системных изменений | Нет upgrade/install проверяемого ПО, рестартов или изменения конфигурации служб |
| A-10 | Стенд малого VPS | Замеры и обоснованные лимиты; нет OOM или недоступности контрольного сервиса |
| A-11 | Проверка артефактов/логов/экспортов и недоверенных входов | Секреты не раскрываются, данные не становятся исполняемыми командами |

Fixtures/моки проверяют корреляцию и сбои. Systemd, права, установщик и ограничения ресурсов проверяются на VM; контейнерный CI сам по себе не доказывает такую поддержку. Все 16 сценариев качества исходного ТЗ сохраняются при детализации тест-плана.

## 12. Выбор основы и следующий этап

Вариант A — Vuls как готовая основа: проверить минимальную конфигурацию, ресурсы и качество данных; доработать onboarding, доставку и необходимые адаптеры. Вариант B — оболочка вокруг Trivy: самостоятельно реализовать состояние, корреляцию, уведомления, health и установку.
