# Проверка Trivy и Vuls на Ubuntu

Дата: 2026-11-06. Статус: **сканеры проверены в runtime на одном Ubuntu-хосте; продукт не реализован**.

## Рекомендация

Для MVP рекомендуется собственный `sec-monitor` с адаптером **Trivy**, без форка движка на старте. Это рекомендация по результатам эксперимента, а не уже утверждённая архитектура.

Оба сканера удалось довести до полноценного результата. Для нашего сценария Trivy оказался проще по ресурсам и быстрее. Критично использовать компактную машинную выдачу: обычный JSON на этом наборе пакетов не прошёл ограничение памяти 1 GiB.

Vuls не отвергается как проект вообще. Проверялся конкретный релиз 0.42.0 с его общей Vuls2 DB; альтернативные сборки базы и централизованная установка не сравнивались.

## Стенд и ограничения

- Ubuntu 24.04.4 LTS, x86_64, RAM 15 934 MiB. Идентифицирующие сведения и полный инвентарь в публичные документы не включены.
- Официальные Linux-архивы [Trivy 0.76.2](https://github.com/aquasecurity/trivy/releases/tag/v0.76.2) и [Vuls 0.42.0](https://github.com/future-architect/vuls/releases/tag/v0.42.0). SHA256 сверены с закреплёнными значениями из GitHub Release API, повторно после передачи на хост. Sigstore-подписи отдельно не проверялись.
- Запуск от существующего непривилегированного пользователя. Transient systemd units: CPUQuota 100%, Nice 10, IOWeight 10, NoNewPrivileges, пустые capabilities, read-only системная FS, запись в отдельный лабораторный каталог. Постоянных служб и таймеров не создавали.
- Swap для процессов проверки запрещён. Trivy compact: MemoryMax 1 GiB, GOMAXPROCS=1, GOMEMLIMIT=600MiB. Финальный Vuls report: MemoryMax 2 GiB, GOMAXPROCS=1, GOMEMLIMIT=1200MiB.
- Только OS-пакеты. Secrets scanning и телеметрия Trivy явно отключены. Во время скана не выполнялись сетевые запросы для определения зависимостей; отдельная загрузка общей vulnerability DB разрешена.
- В Vuls выбран `fast`, только модуль `ospkg`, локальный transport. Более привилегированные режимы не использованы: [код Debian/Ubuntu адаптера](https://github.com/future-architect/vuls/blob/v0.42.0/scanner/debian.go) содержит пути с `apt-get update`.

RSS ниже измерен `/usr/bin/time -v`; это память процесса, а не всей машины. Она может отличаться от charge cgroup из-за mmap/shared pages. Поддержка целого VPS с 1 GiB RAM этим опытом не доказана.

Это отдельные прогоны, не статистическое нагрузочное исследование. Время Vuls report не включает предыдущую инвентаризацию и загрузку базы. Первый полный Trivy cold run с MemoryHigh=768MiB и обычным JSON также завершился cgroup OOM; его длительность 147,53 с не используется как нормальная скорость сканера. Во время этого прогона MemoryHigh был снят, поэтому это диагностическая попытка, а не чистое измерение.

## Что уточнилось о текущем Vuls

Релиз 0.42.0 использует Vuls2 и по умолчанию получает `ghcr.io/vulsio/vuls-nightly-db:0`. Старые описания набора OVAL/CVE словарей не отражают этот путь. См. [инициализацию DB](https://github.com/future-architect/vuls/blob/v0.42.0/detector/vuls2/db.go) и [детектор](https://github.com/future-architect/vuls/blob/v0.42.0/detector/detector.go).

Первую попытку report остановили вручную после создания DB, до завершения отчёта. Transient systemd launcher вернул при штатной остановке код 0, однако поле `reportedAt` оставалось нулевым. Эта попытка **не засчитана успешной**. Финальный повтор с `SkipUpdate=true`, уже готовой DB и ограничением памяти Go завершился полностью: 4 356 CVE, `reportedVersion=0.42.0`, непустой `reportedAt`, `errors=[]`.

Практическое следствие: обвязка должна проверять exit status, завершённость и схему результата, а не принимать один `rc=0` за успех. Успешную предыдущую выдачу нельзя заменять незавершённой.

## Компактная выдача Trivy

Использован штатный `--format template` ([документация](https://trivy.dev/docs/latest/configuration/reporting/)). Вывод состоит из JSONL-записей со следующими полями: target, vulnerability ID, package name и ID, installed/fixed version, severity, source, status, CVSS, primary URL.

Все **51 424** строки проверены против полного JSON: совпадают ключи и перечисленные поля evidence. Это не утверждение о сохранении всех полей полного JSON: длинные описания, весь инвентарь и дополнительные references в экспериментальную проекцию не включались. Для продукта нужен версионированный контракт результата, отдельный inventory snapshot и сохранение необходимого advisory evidence.

Первый compact, cold compact и повторный compact дали одинаковое множество находок по package ID, CVE, установленной/исправленной версии и severity. Загрузка новой DB в этом окне не изменила результат.

Основная причина объёма сырых данных: 51 219 строк относятся к пакетам `linux-*`. Одна CVE повторяется для headers/modules/tools и разных установленных сборок. Хранить связи нужно полностью; в уведомлениях их следует группировать по связанной установке/source package, различать работающее и просто установленное ядро. Нельзя объединять разные assets или терять индивидуальные привязки ради уменьшения числа сообщений.

## Сопоставление результатов и происхождение пакетов

Trivy: 4 345 различных vulnerability ID; Vuls: 4 356. Пересечение — 4 343; только Trivy — 2; только Vuls — 13. Это наблюдаемое расхождение источников и matching, а не оценка количества истинных уязвимостей или полноты сканеров.

Весь vulnerability evidence Trivy в этой OS-проверке обозначен источником Ubuntu. Для записей с fixed version проверено нативным `dpkg --compare-versions`, что установленная версия ниже указанной исправленной: в этом наборе была одна уникальная пара версий, повторённая в 6 300 строках. Это не доказывает доступность версии в настроенном APT-репозитории и не заменяет отдельный backport fixture.

При просмотре расхождений обнаружен важный пример со сторонним NodeSource-пакетом: Vuls пометил часть старых CVE как `needed` по Ubuntu-данным, хотя установленная upstream-ветка новее исправления. Для двух таких CVE исправления опубликованы в Node.js 22.4.1 ([официальное сообщение июля 2024](https://nodejs.org/en/blog/vulnerability/july-2024-security-releases)). Это сильный признак ложных срабатываний из-за происхождения пакета; все остальные расхождения не разобраны и общий вердикт точности не выносился.

Отсутствие этих записей у Trivy также не означает полного покрытия NodeSource: для сторонних репозиториев у сканера есть [документированные ограничения](https://trivy.dev/docs/latest/guide/scanner/vulnerability/). В продукте такой пакет требует vendor adapter либо явного `partial/unsupported/manual_review_required`, а не вывода «безопасен».

## Ошибки, отсутствие изменений и артефакты

Проверен Trivy с отсутствующей DB и `--skip-db-update`: non-zero exit, явная ошибка, выходной JSON не появился. Это подтверждает данный путь отказа сканера, но не является тестом ещё не существующей очереди или state machine `sec-monitor`.

До/после совпали SHA256 `/var/lib/dpkg/status`, APT source configuration и SSH daemon configuration, а также размеры и timestamps APT list files. Список running service names совпал; само по себе это не доказывает отсутствия всех возможных перезапусков. Наши команды не обновляли пакеты/индексы, не меняли настройки приложений и не перезапускали рабочие службы.

Полный инвентарь, реальные версии/пути и сырые отчёты остаются в приватном лабораторном каталоге на хосте; JSON-отчёты сжаты. Большие DB и архивы загрузок после измерений удалены. Лабораторные units завершены; периодический мониторинг не включён. В репозиторий сохранены только обезличенные [метрики и контрольные результаты](evidence/scanner-evaluation-2026-11-06.json). Частные локальные материалы исключены через `.gitignore`.

Не проверены: Debian runtime, WordPress, language dependencies, контейнерные образы, Telegram, полноценный жизненный цикл фиксов, синтетические backport fixtures, происхождение всех пакетов, потеря питания и доставка outbox. Не выполнен полный аудит уязвимостей данного сервера и не измерено влияние на конкретное веб-приложение.

## Следующее решение

Согласовать Trivy как движок MVP и уточнить PRD/технический план вокруг собственного слоя inventory/origin, корреляции, группировки, хранения, уведомлений и health. Для небольшого VPS принять компактную выдачу и отсутствие телеметрии как проверяемые требования. Минимальный ресурсный профиль окончательно подтвердить отдельно на ограниченном Linux-стенде, затем проверить Debian.
