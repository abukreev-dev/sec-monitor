# Техническое задание: Security Monitor для VPS/VDS

**Версия:** 1.0  
**Дата:** 06.11.2026  
**Назначение:** передача локальному агенту Codex с доступом к серверу  
**Язык реализации/документации:** Python 3 / русский  
**Стоимость:** использование бесплатного/open-source ПО и бесплатных публичных источников; без обязательных подписок  
**Статус:** ТЗ на обследование, проектирование, реализацию, тестирование и развёртывание

> **Задание агенту:** реализовать реально работающий сервис, а не демонстрационный скрипт. Начать с инвентаризации и плана изменений, затем разработать, проверить на синтетических данных и только после этого установить. Не менять конфигурацию веб-сервера, WordPress, БД, firewall, SSH и работающих сайтов без отдельного явного одобрения владельца. НИКОГДА не выполнять автоматическое обновление ОС/пакетов/плагинов по инициативе этого монитора. Если необходимые реквизиты (например, токен Telegram или ключ Wordfence) отсутствуют, завершить развёртывание в ограниченном режиме и перечислить недостающие настройки; не выдумывать токены.

## 1. Цель и границы

Создать на VPS/VDS с root-доступом лёгкий локальный сервис **Security Monitor**, который:

1. Автоматически инвентаризирует фактически установленные и используемые компоненты серверного стека.
2. Находит известные уязвимости в пакетах ОС, приложениях и зависимостях, контейнерных образах (если они используются), ядре WordPress, плагинах и темах (если WordPress установлен).
3. Получает ранние сигналы из бесплатных внешних источников, включая CISA KEV, официальные security advisories и Wordfence Intelligence для WordPress; не зависит исключительно от момента появления записи в базе сканера.
4. Сопоставляет уязвимости с установленной версией и фиксирует степень уверенности в применимости.
5. Указывает, есть ли **доступное** исправление для данного продукта/репозитория; отдельно показывает, **установлено** ли исправление; не смешивает эти статусы.
6. Отправляет в Telegram только новые существенные события, изменения статусов, деградацию мониторинга и регулярную сводку; предотвращает спам и дубли.
7. Работает автономно по `systemd`-таймерам, сохраняет историю и предоставляет удобные локальные CLI-команды.
8. Не создаёт существенной нагрузки на продакшен-сайты и не требует Wazuh/Elasticsearch/PostgreSQL/Redis.

**Не входит в MVP:** автоматическое обновление системных пакетов или WordPress, эксплуатация уязвимостей, активное сканирование внешних сервисов, непрерывный сетевой IDS, управление исправлениями как MDM/RMM, публичный веб-интерфейс, обещание полного покрытия всех CVE. Возможность расширений должна быть предусмотрена архитектурно.

## 2. Важнейшие принципы

- **Read-only по умолчанию.** Проверки могут читать системные сведения и обращаться к внешним API, но не модифицируют сайт, конфигурацию сервисов или пакеты. Установка самого монитора и его зависимостей — только после согласованного плана.
- **Надёжность важнее количества алертов.** Не выдавать статус `affected` без доказанного сопоставления продукта/версии или с высоким уровнем неопределённости; для неоднозначных случаев использовать `potentially_affected`.
- **Backports.** Для пакетов Debian/Ubuntu/RHEL-подобных ОС приоритет имеют данные security advisories дистрибутива, а не прямое сравнение upstream-версий. Сторонние репозитории учитывать отдельно.
- **Источник и время.** Каждая находка должна содержать URLs, идентификатор источника, время публикации (если доступно), время первого обнаружения монитором и время последней проверки.
- **Отсутствие данных ≠ безопасность.** Ошибка API, просроченная база, неподдерживаемый продукт, отсутствие сканирования или исчезновение CVE из выдачи не означают, что проблема исправлена.
- **Проверка реальности фикса.** `fix_available`, `update_installed` и `remediated_verified` — разные события.
- **Приватность.** Инвентарь сервера, версии ПО и токены не публикуются в открытых API, кроме минимально необходимых параметров для согласованных запросов; Telegram-сообщения без секретов и чувствительных путей.

## 3. Этап 0 — обязательная инвентаризация (до любых изменений)

Создать и выполнить **только читающий** скрипт `scripts/discover.sh` или равноценный Python-модуль. Сохранить отчёт в локальный файл с доступом только администратору. Не отправлять наружу инвентарь целиком.

Определить:

- ОС, точная версия, архитектура, ядро, виртуализация; поддерживаемость дистрибутива и срок security support.
- CPU, RAM, swap, свободное место и I/O-профиль, ограничения контейнеризации и systemd; выбрать безопасные лимиты.
- Системный пакетный менеджер (APT/DPKG, DNF/RPM и др.); подключённые репозитории и origin каждого критического пакета, held/pinned packages.
- Веб-серверы: nginx, Apache, LiteSpeed/OpenLiteSpeed, версии и способ установки; reverse proxy, PHP-FPM, CLI PHP (все установленные параллельные версии), расширения PHP.
- Базы данных: MariaDB, MySQL, PostgreSQL, Redis, версии; различать локальные и удалённые экземпляры.
- OpenSSL, OpenSSH, curl, glibc, systemd и другие критичные пакеты.
- Нестандартные бинарники, системные сервисы и панели управления (например, ISPmanager, HestiaCP, aaPanel, Plesk, DirectAdmin, Beget-специфические компоненты), источники их security updates и ограничения лицензирования.
- Docker/Podman/containerd, работающие контейнеры, образ+digest, Compose-файлы, используемые образы, Kubernetes при наличии.
- Каталоги сайтов и приложения: WordPress (включая multisite), иные CMS, Composer lock, package-lock/yarn/pnpm lock, Python requirements/poetry/uv, системные и пользовательские crontab. Ничего не исполнять из непроверенных проектов.
- Наличие WP-CLI и его работоспособность под **пользователем сайта**; WordPress core, плагины (включая неактивные, MU/drop-ins), темы (включая неактивные), slug, версии, тип источника и auto-update status.
- Наличие системных механизмов обновления безопасности (`unattended-upgrades`, `dnf-automatic`), не изменяя их настройки.
- Доступность HTTPS до источников и Telegram, DNS и синхронизация системного времени.
- Присутствуют ли уже Trivy или другие сканеры; совместимость и существующие задачи мониторинга.

**Результат этапа:** `docs/INVENTORY.md` с обезличиванием секретов, `docs/IMPLEMENTATION_PLAN.md` с выбранными адаптерами, ограничениями покрытия, предполагаемой нагрузкой и точным списком системных изменений. Перед установкой требовать одобрение владельца на предложенные изменения. Если агент работает автономно без возможности получить одобрение, ограничиться подготовкой к развёртыванию и тестами, не совершая потенциально влияющих на продакшен действий.

## 4. Архитектура

Технологии: Python 3 из репозитория ОС (в совместимой поддерживаемой версии); виртуальное окружение для приложения; SQLite для состояния; Trivy CLI для сканирования; `systemd` oneshot services + timers; HTTPS API источников; Telegram Bot API. Без постоянного слушающего порта в базовой установке.

Модули:

1. `inventory` — сбор точных версий и происхождения компонентов, сохранение снимков.
2. `scanners/trivy` — сканер OS/language dependency/container image; безопасная обработка JSON и ошибок запуска.
3. `scanners/packages` — check of package manager advisories и доступных обновлений с учётом backport.
4. `scanners/wordpress` — WP-CLI inventory, Wordfence feed mapping, optional external source adapter.
5. `feeds/kev` — CISA KEV JSON.
6. `feeds/advisories` — официальные security advisories выбранного дистрибутива и реально установленного стороннего ПО; адаптеры вместо бездумной подписки на весь NVD.
7. `feeds/osv` — необязательная проверка зависимостей по OSV API при наличии точных package ecosystem/name/version; не заменяет Trivy.
8. `correlator` — нормализация CVE/GHSA/Wordfence ID, сопоставление затронутых версий, происхождения пакетов, состояния исправления, приоритета и уверенности.
9. `state` — SQLite, история событий и дедупликация.
10. `notifier/telegram` — сообщения, повторные попытки, дайджест, проверка доставки.
11. `health` — диагностика свежести источников, успешности сканов, системных таймеров и ресурсоёмкости.
12. `cli` — диагностика, статус, ручной запуск, отчёт, тест уведомления, экспорт.

**Внешний мониторинг heartbeat:** желательно (но необязательно для MVP) добавить бесплатный внешний dead-man check, например самостоятельно выбранный сервис с бесплатным тарифом или отдельный независимый узел. Сам монитор на упавшем VPS сообщить о падении не может. Не регистрировать внешнюю услугу без разрешения владельца.

## 5. Источники и способ их использования

### 5.1 Trivy — основа проверки реально установленных пакетов

Использовать официальный поддерживаемый способ установки для фактической ОС, с проверкой ключа подписи репозитория и pinning источника; не использовать `curl | bash` от root без проверки. Версию Trivy логировать. Команды и флаги проверять с установленной версией (`trivy --help`).

Рекомендуемые логические операции (синтаксис уточнить по установленной версии):

```bash
trivy rootfs --pkg-types os --scanners vuln --format json --output <private-path>/trivy-os.json /
trivy fs --scanners vuln --format json --output <private-path>/trivy-app.json <safe-app-path>
trivy image --scanners vuln --format json --output <private-path>/trivy-image.json <image@digest>
```

Обязательно:

- ограничивать время/CPU/параллельность/приоритет задачи (`timeout`, `nice`, `ionice` если доступен, `systemd` `CPUQuota`, `MemoryMax`, `IOWeight`/`Nice` по результатам измерения);
- сканировать только найденные нужные каталоги зависимостей и контейнерные образы; не проводить бессмысленный полный обход `/` каждые 15 минут;
- исключить виртуальные FS, mounts, резервные копии, медиаархивы, кэши и каталоги с секретами, если они не требуются для проверки; запретить secrets scanning по умолчанию;
- безопасно читать результат атомарно: временный файл → проверка валидности и кода возврата → rename; не заменять успешную базу пустым/повреждённым результатом;
- отличать уязвимости без фикса (`FixedVersion` отсутствует) от ошибок или неподдерживаемого продукта;
- не использовать `--ignore-unfixed` в хранилище (иначе потеряем информацию о появлении исправления); фильтровать только на уровне уведомлений;
- документировать ограничение: сторонние и собранные вручную пакеты могут не попадать под проверку Trivy, необходимы отдельные vendor adapters.

### 5.2 Пакетный менеджер и статус исправлений

**Debian/Ubuntu:** определить доступные обновления и security-репозитории через APT без фактического `upgrade`; использовать источники Debian Security Tracker/Ubuntu security notices и доступные package metadata. Не делать `apt update` конкурирующим с другими операциями без проверки блокировок; использовать штатные механизмы и согласованный график. Для сравнения пакетов использовать `dpkg --compare-versions` или Python-binding к dpkg, а не лексикографию.

**RHEL/AlmaLinux/Rocky:** DNF updateinfo/security advisories при поддержке репозиторием; RPM version comparison; не обобщать «доступен патч» на основании только upstream release.

**Другие ОС:** отдельный адаптер с явным status `unsupported` до реализации.

Для каждого события `fix_available` нужны доказательства: установленная версия, доступная версия (из доверенного репозитория), идентификатор бюллетеня/источник и способ сравнения. Если upstream исправление есть, но обновлённого пакета в репозитории нет: `upstream_fix_available`, но НЕ `repo_fix_available`.

### 5.3 WordPress

Если WordPress найден, вызвать WP-CLI **от uid/gid владельца сайта**, без `--allow-root`. Избегать выполнения произвольных хуков плагинов при инвентаризации: насколько поддерживается, использовать `--skip-plugins --skip-themes`; учитывать MU-плагины, которые могут загружаться даже при этих флагах. Для небезопасной установки WP-CLI предусмотреть fallback read-only-парсинга метаданных файлов и статус `partial_inventory`. Не запускать внешние PHP-скрипты, найденные в дереве, без анализа риска.

Данные: core version, plugin/theme slug, installed version, active/inactive, source, availability of update, multisite site identity. Сопоставлять с **Wordfence Intelligence V3** (`https://www.wordfence.com/help/wordfence-intelligence/v3-accessing-and-consuming-the-vulnerability-data-feed/`), API token через `Authorization: Bearer ...`; production/scanner feed выбирать по назначению и размеру. Кэшировать полную выдачу, соблюдать 429, retry-after/backoff, ограничения и лицензию; не полагаться на старые unauthenticated V1/V2.

Для Wordfence учитывать UUID записи, CVE (если есть), тип продукта, slug, диапазоны версий с включёнными/исключёнными границами, patched flag и patched_versions. Реализовать тесты для `*`, `<=`, `<`, `>=`, `>`, pre-release и нестандартных версий WordPress. Неактивный уязвимый плагин всё равно может быть значим — не игнорировать его автоматически. При сомнительном slug/версии ставить `potentially_affected` и давать ссылку для ручной проверки.

**Webhook Wordfence:** опционально, только если уже есть безопасная HTTPS-инфраструктура и после отдельного одобрения. Базовая схема — polling, без публичного HTTP endpoint. Если включить webhook, проверять HMAC-SHA256 по исходному телу, сравнивать constant-time, ограничивать размер/частоту, логировать только безопасные метаданные. Точное имя signature header проверить в актуальной документации (в ней встречаются различающиеся обозначения); не принимать неподписанные сообщения.

### 5.4 CISA KEV

Официальный машиночитаемый каталог:
`https://github.com/CISAGov/kev-data` (JSON и schema).

Проверять новые записи и изменения. Сопоставлять по CVE с установленными продуктами и находками сканирования. KEV означает **подтверждённую эксплуатацию где-то в мире**, а не факт компрометации нашего сервера. Для неподтверждённой применимости выводить «KEV — потенциально относится к установленному продукту», но не «сервер взломан».

### 5.5 Ранние security releases и иные источники

По результатам инвентаризации включить в конфигурацию **официальные** источники производителя для каждого критичного компонента, в том числе:

- ОС: Debian Security Tracker / Debian Security Advisories; Ubuntu Security Notices; RHEL/AlmaLinux/Rocky advisories в зависимости от фактической ОС;
- PHP: официальные PHP releases/security advisories, если используется upstream/нестандартная сборка; иначе первичны advisories дистрибутива/репозитория;
- nginx, Apache HTTP Server, OpenSSL, OpenSSH, MariaDB/MySQL/PostgreSQL, Redis, панели администрирования — только для установленных продуктов;
- WordPress core security releases (`https://wordpress.org/news/category/security/`) и Wordfence feed;
- Docker/container runtime — официальные advisories и реальное сканирование используемых образов;
- языковые зависимости — Trivy и, при необходимости, OSV (`https://google.github.io/osv.dev/api/`).

Не реализовывать хрупкий парсинг произвольного HTML как единственный сигнал: предпочитать RSS/Atom/JSON/API/security repositories; адаптер с HTML должен иметь тестовый fixture и сигнализировать при изменении формата. Отдельно учесть источники для ПО из сторонних репозиториев и самосборных бинарников — если автоматизированный источник невозможен, явно показывать `manual_review_required` и не делать ложное утверждение о полном покрытии.

**OpenCVE:** необязательное внешнее дополнение для ручного наблюдения, не обязательная зависимость MVP; система должна функционировать без OpenCVE и платных тарифов.

### 5.6 Фиксы и жизненный цикл находки

Состояния (не смешивать):

- `new_untriaged` — новый advisory/CVE, применимость не установлена;
- `potentially_affected` — продукт совпадает, версия/сборка или условия неоднозначны;
- `affected` — затронутая установленная версия подтверждена по выбранному источнику;
- `not_affected` — доказуемо не затронуто;
- `upstream_fix_available` — исправление опубликовано upstream;
- `repo_fix_available` — исправленный пакет есть в фактическом репозитории;
- `update_installed_pending_verification` — подтверждено изменение установленного пакета/версии, проверка ещё не завершена;
- `remediated_verified` — исправленная сборка установлена и повторная проверка подтверждает устранение;
- `mitigated` — применено временное снижение риска (только по подтверждённым данным/ручному подтверждению);
- `no_fix_available`, `unsupported`, `source_stale`, `scanner_error`, `false_positive_reviewed`.

Предусмотреть независимые поля `applicability_status`, `fix_status`, `remediation_status`, `scan_health`, поскольку у одной CVE могут одновременно быть `affected` и `repo_fix_available`. Список выше — значения соответствующих полей, а не одна взаимоисключающая enum.

Сроки и переходы фиксировать в истории. Исчезновение CVE из одного скана **не переводит** в `remediated_verified` без проверки пакета/версии или достоверных обновлённых vendor advisories; при сомнениях `needs_reverification`.

## 6. Корреляция, приоритеты и дедупликация

**Уникальность находки:** `server_id + asset_id + component_identity + vulnerability_canonical_id`; принимать связанные ID (CVE, GHSA, Wordfence UUID, OSV) с возможностью alias mapping. Не объединять разные уязвимости по одному лишь похожему заголовку. Учитывать, что одна CVE затрагивает несколько компонентов/сайтов.

Уровни:

- **P1 (немедленно):** CISA KEV + подтверждённая применимость; либо RCE/auth bypass на внешне доступном компоненте при подтверждённой применимости и высоком риске; либо прямо подтверждённая эксплуатация из заслуживающего доверия источника.
- **P2:** confirmed affected, CVSS ≥ 8.0 или security advisory высокого уровня/экспозиции; а также появление патча к открытой P1.
- **P3:** прочие подтверждённые проблемы, сомнительная применимость, новые релизы и обновления без доказанной критичности.
- **SYSTEM:** источник не отвечает, база устарела, сканер сломан, не отправляются сообщения или превышен лимит ресурсов.

CVSS v3/v4 указывать с версией и источником; не выдавать оценку по умолчанию, если её нет. EPSS — опциональное улучшение, не условие MVP. Степень внешней доступности определять по конфигурации и локальным слушающим сокетам, не делать неконтролируемые внешние пробные атаки.

События: `new_finding`, `severity_changed`, `kev_added`, `exploit_evidence_added`, `fix_published`, `repo_fix_available`, `update_detected`, `remediation_verified`, `finding_reopened`, `scan_failed`, `feed_stale`, `feed_recovered`, `daily_digest`.

**Антиспам:** отдельный event fingerprint, durable outbox с idempotency key; повтор только при существенном изменении; aggregation batch при массовом появлении уязвимостей; ограничение количества сообщений за окно; P1 не теряется из-за лимитов — уходит отдельным сообщением либо срочной сводкой с подсчётом и ссылкой на локальный отчёт (без открытой публикации).

## 7. Telegram

Использовать официальный Bot API `https://core.telegram.org/bots/api`; `sendMessage` через HTTPS с timeout/retry/backoff. Бот отправляет сообщения в заданный chat_id; входящие команды не нужны в MVP (никакой long polling listener не требуется). Предусмотреть поддержку MarkdownV2/HTML с корректным escaping либо plain text, чтобы сообщения не ломались из-за спецсимволов и данных из advisories.

**Шаблон P1/P2 (русский):**

```
🚨 Security Monitor — P1
Сервер: <короткий псевдоним>
Компонент: <продукт> / <пакет>
CVE: <идентификатор + URL>
CVSS: <оценка, версия, источник> / KEV: да/нет
Установлено: <версия/сборка>
Применимость: подтверждена | вероятная | неизвестна
Эксплуатация: подтверждена в мире | нет подтверждения
Патч upstream: да/нет/неизвестно
Патч в репозитории: да/нет/неизвестно
Рекомендация: <проверяемое безопасное действие>
Источник: <доверенный URL>
Обнаружено: <локальное время + timezone>
```

Для `remediation_verified` включать установленную исправленную версию, дату установки/обнаружения, ссылку на advisory и время успешной перепроверки. Для SYSTEM — точное название отказавшего адаптера и период отсутствия свежих данных.

При первом запуске: Telegram test + **baseline digest**, но не рассылать по одному сообщению на все старые CVE. Новые последующие находки уведомлять обычно.

Секреты: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `WORDFENCE_API_KEY` в root-owned env-файле `0600`, вне Git. Не выводить их в stdout, traceback или debug. Файл `.env.example` только с плейсхолдерами; в ошибках маскировать токены и URL с секретами.

## 8. Планировщик и нагрузка

Интервалы по умолчанию (параметризуемые):

| Задача | Период | Примечание |
|---|---:|---|
| KEV и лёгкие advisory feeds | 15 минут | conditional GET (`ETag`, `If-Modified-Since`) если поддерживается |
| Wordfence feed | 60 минут | учитывать полный объём feed, HTTP 429 и разрешённые лимиты; webhook опционально |
| Пакетные обновления / inventory | 60 минут | без установки обновлений и конкуренции за package locks |
| Trivy OS | 6 часов | в часы минимальной нагрузки, с jitter |
| Trivy dependencies | 12–24 часа | только найденные проекты |
| Контейнерные образы | 24 часа и при изменении digest | если используются |
| WP inventory | 1 час | без обновлений и установки |
| Полная сверка/состояние | 24 часа | фиксы, закрытие, integrity check SQLite |
| Дайджест | 1 раз в сутки | локальное время владельца, конфиг |
| Health self-check | 15 минут | stale thresholds и failures |

Не выполнять параллельно тяжёлые сканы на малом VPS. `flock`/`systemd` serialization, randomized delay и backoff. Интервалы адаптировать после измерения реальных ресурсов. При превышении лимита прекратить конкретную задачу с тревогой; веб-сайт важнее сканирования.

## 9. Каталог данных и SQLite

Рекомендуемые таблицы (можно менять после обоснования):

- `assets` — сервер/сайт/контейнер, расположение, тип, владелец, last_seen;
- `components` — asset, ecosystem, vendor, canonical product, slug/package, installed version, origin/repo, runtime exposure, discovered_at;
- `advisories` — canonical_id, aliases, summary, severity/cvss, exploitation evidence, source URLs, published/modified;
- `affected_components` — ключ компонента+advisory, статус применимости, доказательство, данные о затронутых версиях;
- `fixes` — upstream fixed version, repo fixed package version, repo name, status/evidence;
- `findings` — first_seen, last_seen, current state, priority, risk attributes;
- `finding_events` — immutable event history, before/after, source;
- `feed_runs` и `scan_runs` — success/error/duration, last success, feed published-at, staleness;
- `notification_outbox` — idempotency key, event, attempts, sent_at, failure, next_retry;
- `settings/snapshots` — schema version, config hash, last known inventory.

SQLite: WAL при корректной локальной FS, миграции с версионированием, транзакции, индексы по уникальности и времени, ротация/retention, резервное копирование и проверка целостности. Отдельно сохранять минимальные диагностические JSON-артефакты сканирования с ограниченным сроком жизни (например, 14 дней), без секретов и dump содержимого сайтов.

## 10. CLI и эксплуатационные команды

Обязательные команды (имена как пример, но единообразно описать в README):

```text
security-monitor discover --read-only
security-monitor status
security-monitor health
security-monitor scan --target os|apps|wordpress|containers|all
security-monitor feeds refresh --source kev|wordfence|all
security-monitor report --format text|json --severity P1,P2
security-monitor report --open-only
security-monitor notifications test
security-monitor notifications retry-failed
security-monitor doctor
security-monitor version
```

`status` должен показывать по каждому адаптеру: installed/enabled, последняя успешная проверка, длительность, fresh/stale/error, возраст локальной базы, количество открытых P1/P2/P3, число доступных исправлений и ошибок отправки Telegram. `doctor` проверяет конфигурацию, права, таймеры, доступность API, место на диске и версию Trivy, не раскрывая ключи.

## 11. Файловая структура и установка

Рекомендуемый репозиторий:

```text
security-monitor/
  README.md
  pyproject.toml
  LICENSE
  .gitignore
  config.example.yaml
  .env.example
  src/security_monitor/{cli,config,inventory,feeds,scanners,correlator,storage,notifier,health}/
  migrations/
  tests/{unit,integration,fixtures}/
  scripts/{discover.sh,install.sh,uninstall.sh,backup.sh}/
  deploy/systemd/{security-monitor-*.service,security-monitor-*.timer}
  docs/{INVENTORY.md,IMPLEMENTATION_PLAN.md,OPERATIONS.md,SECURITY.md,COVERAGE.md}
```

Рекомендуемая установка: код `/opt/security-monitor` с контролируемыми правами; конфиги `/etc/security-monitor/` (секреты 0600); БД `/var/lib/security-monitor/` (0700); журналы в journald, ограниченный размер; cache в `/var/cache/security-monitor/`.

Минимизация привилегий: отдельный системный пользователь для сетевых API/обработки/БД/Telegram, отдельные строго ограниченные root-процессы для чтения системных метаданных только если реально необходимо. Не запускать постоянно Python-сервис от root. Избегать передачи секретов через argv и появления их в списке процессов. Для `systemd` использовать подходящие sandbox/hardening directives (`NoNewPrivileges`, `ProtectSystem`, `ProtectHome` с разрешениями на нужные пути, `PrivateTmp`, `UMask=0077`, ограничения capabilities), проверив совместимость с конкретными операциями сканирования. Не допускать на продакшене падения штатных сервисов из-за несовместимых ограничений.

Инсталлятор должен быть **идемпотентным**; uninstall удаляет только собственные службы/таймеры/код и по выбору данные, не трогает Trivy/пакеты, установленные независимо. Предусмотреть dry-run, сохранение существующего состояния и rollback; ни один этап не должен перезапускать nginx/Apache/PHP-FPM/MariaDB/MySQL/Docker.

## 12. Тестирование и требования к качеству

Юнит-тесты обязательны:

1. Чтение корректного/битого/пустого Trivy JSON; timeout и ненулевой exit-code не удаляют предыдущие валидные находки.
2. Version matching для DPKG/RPM/PHP/WordPress; диапазоны Wordfence и граничные включения/исключения.
3. Backported fix: upstream версия выглядит уязвимой, а vendor security package исправлен → не выводить ложную активную уязвимость.
4. Появилась новая CVE без патча → `affected`, `no_fix_available`; позже патч появился → событие `fix_published`; repo package доступен → `repo_fix_available`.
5. Обновление пакета не подтверждает исправление до повторной верификации.
6. Новый KEV для уже открытой находки повышает приоритет и создаёт ровно одно событие.
7. Одна CVE в разных сайтах/контейнерах не теряется при дедупликации.
8. Повторный запуск с идентичной информацией не отправляет новых сообщений.
9. HTTP 429, 500, timeout, schema drift, stale feed; retry/backoff и HEALTH-сигнал.
10. Telegram ошибка/недоступность, очередь доставки, retry идемпотентно на уровне приложения (учитывать, что сетевой timeout после приёма Telegram может дать редкий дубль).
11. Инъекция строк в заголовках advisories и путях не приводит к shell injection/Markdown injection.
12. Секреты отсутствуют в логах, exception traces, экспортируемых отчётах.
13. `systemd timer` переживает reboot; задачи не работают внахлёст.
14. Несколько параллельных PHP версий, несколько WP сайтов и Docker образов.
15. Отсутствие WordPress/Docker не считается ошибкой.
16. Неподдерживаемая ОС/сторонний пакет отображается как coverage gap, а не «уязвимостей нет».

Интеграционные тесты — на fixtures и mocked API, не требующие публикации секретов. Smoke test на сервере — только безопасный, с явной проверкой влияния на ресурсы. Нагрузочное измерение CPU/RAM/disk/time сделать до и после включения таймеров.

## 13. Критерии приёмки

Работа считается выполненной только если:

- [ ] Доступны `INVENTORY.md` и `COVERAGE.md` со списком всех обнаруженных компонентов и указанием: покрыт / частично / не покрыт / ручной источник.
- [ ] Развёрнут код, SQLite, рабочие systemd services/timers и документированная схема запуска.
- [ ] Trivy сканирует поддерживаемые системные пакеты, реальные зависимости проектов и используемые контейнерные образы при их наличии.
- [ ] WP inventory и Wordfence V3 работают при наличии WordPress и ключа; без ключа есть явная ошибка конфигурации, а не молчаливый пропуск.
- [ ] KEV регулярно проверяется, а изменения KEV коррелируют с локальными находками.
- [ ] Для каждого уровня P1/P2 показываются доказательства применимости и URL первоисточников.
- [ ] Состояния `affected`, `patch available`, `patch installed`, `verified fixed`, `unknown` различаются и проходят тесты.
- [ ] Тестовое Telegram-сообщение успешно доставлено и подтверждено владельцем (при предоставленных реквизитах).
- [ ] Повторное сканирование без новых событий не спамит Telegram.
- [ ] Неуспешное сканирование/просроченные базы вызывает отдельное предупреждение, но не закрывает старые находки.
- [ ] Задачи не оказывают заметного влияния на доступность сайта; лимиты ресурсов и интервалы зафиксированы.
- [ ] Репозиторий содержит тесты, README, инструкции установки/rollback, описание угроз и ограничения.
- [ ] Не настроены автоматические обновления без отдельного разрешения; не открыты новые публичные порты.
- [ ] По окончании выполнены `doctor`, `status`, тест кейсов и выдан итоговый отчёт с командами эксплуатации.

## 14. План работ для Codex

**Фаза A — аудит без изменений.** Инвентаризация, перечень источников и coverage gaps, план изменений, оценка ресурсов. Не устанавливать пакеты на этом этапе.

**Фаза B — локальный MVP в рабочем каталоге.** Базовая архитектура, SQLite, адаптер Trivy, KEV, package manager, Telegram, CLI, fixtures, unit tests, dry-run. Работать на локальных синтетических данных без Telegram токена и без изменения prod.

**Фаза C — расширения под фактический стек.** WordPress/WP-CLI/Wordfence, сторонние репозитории, используемые контейнеры, официальные release advisories. Обязательный coverage matrix.

**Фаза D — безопасное развёртывание после разрешения.** Согласовать список установок/пакетов, лимиты и таймеры; установить; smoke test; доставка тестового сообщения; базовый отчёт; мониторинг ресурсоёмкости.

**Фаза E — приёмка и документация.** Провести все тесты, зафиксировать недостающие источники и ограничения, инструкции рутинной эксплуатации, восстановления после сбоя и обновления самого монитора.

**Приоритеты:** сначала надёжный, наблюдаемый read-only MVP; затем расширение покрытия. Не тратить время на веб-панель, Docker Compose или крупные инфраструктурные компоненты, если это не обусловлено аудитом.

## 15. Что агент обязан выдать владельцу по окончании

1. Краткое резюме фактически найденного стека (без паролей, IP по возможности маскировать).
2. Реализованные и не реализованные проверки, причины пробелов и риски ложных отрицаний.
3. Список файлов и внесённых изменений в систему.
4. Версии установленных инструментов, статус таймеров и результат тестового Telegram-уведомления.
5. Таблицу P1/P2 и доступных фиксов без утечки чувствительных данных.
6. Команды ручного сканирования, диагностики, восстановления БД, резервного копирования, остановки мониторинга и отката.
7. Явное подтверждение: не выполнялись обновления/рестарты production-компонентов; если понадобились — перечислить и запросить отдельное разрешение.
